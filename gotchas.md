# Gotchas

Distilled working knowledge for agents and collaborators in this repo. Append entries; keep each a few lines.

- **No process ceremony with Harper.** Don't announce skill usage, workflow compliance, or plans-before-acting. He interrupted mid-task to stop it ("please stop"). Keep the discipline (verify, be honest about what ran), skip the narration — the first visible action should be real work.
- **Canonical check is `uv run docs/validation/check.py`.** Run it after touching anything in `docs/`; append a dated revision to `docs/VALIDATION.md` with the real output. Never rewrite earlier revisions — they're the historical record.
- **`gofmt -l` exits 0 even when it lists unformatted files.** Chaining `gofmt -l ... && git commit` commits unformatted code (burned two commits this way). The gate is `scripts/check`, which captures the output and fails on non-empty; use it, not ad-hoc chains.
- **Go toolchain here needs `env -u GOROOT mise exec -- go ...`** — inherited GOROOT points at a removed toolchain. `scripts/check` self-heals this; direct `go` invocations don't.
- **`go mod tidy` prunes deps nothing imports yet.** Add a dep with `go get` only after code imports it, or tidy will silently drop it and the next build fails with "no required module provides package".
- **golangci-lint caps duplicate findings at 3 per message** (`max-same-issues`), so "21 issues" can understate. Errcheck noise categories are excluded via `.golangci.yml` (`std-error-handling` preset); genuine ignores stay explicit `_ =` in code.
- **§5.2 state matrix: no direct live→stopped transition.** `running` and `paused` must go through `stopping` before reaching `stopped`. Force-stop and force-delete paths both need the intermediate step. A direct `→stopped` attempt returns `InvalidTransitionError`.
- **Manager.Close() must call `wg.Wait()` BEFORE `cancel()`.** Cancelling context first makes in-flight goroutines' store calls fail immediately, leaving VMs stuck in transitional states. The correct order: drain workers, then cancel.
- **Testing semaphore caps: use store state, not goroutine timing.** Goroutine-side "inflight" counters can show peak > cap even when the semaphore is working correctly (goroutine activity spans longer than semaphore occupancy). Count VMs in "starting" state instead — a VM stays there while its Launch call is blocked inside the semaphore slot.
- **`config.Admission{}` zero value → 0 usable vCPU, zero memory usable.** `CPUOvercommitRatio: 0` makes `UsableVCPU()` return 0, causing every VM create to be refused for CPU. Test managers that create VMs need `CPUOvercommitRatio > 0` (e.g. `4.0`). The existing `newServer` helper (empty templates, zero admission) is fine for non-VM tests; VM tests need `newTemplateServer` / `newVMServer`.
- **Go `flag.FlagSet.Parse` stops at the first non-flag token.** `vm create NAME --template ID` never parses `--template` because `NAME` is a non-flag. Flags must come before positional args: `vm create --template ID NAME`. This is the standard Go flag-package contract.
- **`api.New` requires `*runtime.Manager` (not optional).** Passing nil panics on the first endpoint that calls `s.manager`. All three test helpers (`api_test.go:newServer`, `working_set_test.go:TestSituationResponseByteBound`, `cmd/vmobs/main_test.go:newServer`) must build a minimal manager with a fake runtime and pass it.
- **Batch idempotency: NULL idempotency_key is outside idempotency scope.** Two batch creates without a key never replay each other — the UNIQUE partial index only covers non-null keys (`WHERE idempotency_key IS NOT NULL`). This matches the single-VM convention.
- **best_effort cumulative totals: in-tx reads see own uncommitted inserts.** `reservationTotalsInTx` re-reads inside the single-writer tx after each admitted member's reservation is inserted. This is the AT-012 serialization point for best_effort; SQLite single-writer guarantees the running total is correct. Never call the admission callback with totals captured before the tx starts.
- **batchCoord.remaining must be initialized before goroutines launch.** `newBatchCoord` sets `remaining` to `len(members)` via atomic store; constructing `batchCoord{}` directly leaves remaining at zero, so the first `memberDone` decrements it to -1 and the `== 0` finalization check never fires — the batch op stays `running` forever.
- **Batch-level operation kind is `vm_batch.create`, not a registered event kind.** It lives in the operations table; event kinds (events registry) are for events table rows. Don't add `vm_batch.create` to `internal/events`.
- **Launch-path transitions must carry a `From` pin.** `stopped→starting` is a legal restart edge, so an unpinned launch transition can revive a VM that was stopped while the launch job sat queued (user stop or batch stop wave). Every transition made on behalf of an async job pins `From` to the state it expects; a refused pin means someone superseded the job — walk away, don't retry unpinned.
- **Op finalizers use `IfState: "running"`.** `UpdateOperation` without a guard rewrites terminal evidence — the batch stop wave used to flip already-succeeded launch ops to failed. Guarded updates return `ErrOperationStale` on mismatch, touch nothing, and emit no event. Any new code path that finalizes an operation it doesn't exclusively own must pin IfState.
- **Run reportGen must be wired before NewManager if needed during Reconcile.** `Reconcile` (called inside `NewManager`) re-enqueues report generation for terminal runs missing stored reports. If `SetReportGen` is called after `NewManager`, the report reconcile sweep sees a nil generator and skips. Use `NewManagerWithReportGen` to wire the generator before the initial reconcile fires.
- **Run hooks must distinguish launch-fail from ordinary VM-terminal.** `onVMLaunchFailed` uses `triggerLaunchFail` which produces the R8 reason ("vm launch failed before the run started"). `onVMTerminal` uses `triggerVMTerminal`. Never call `onVMTerminal` from `failLaunch` or the run gets the wrong reason and the R8 path is untestable.
- **`concludeRun` From pin: loser walks away silently.** Every conclusion path (VM hook, SubmitRunResult goroutine, ConcludeRun) calls `TransitionRun` with a From pin. `InvalidRunTransitionError` means the race was lost — return the current run state, never surface the error to the caller. This is how concurrent VM-stop + result-submit resolves to exactly one terminal phase.
- **vm_id= has one semantic everywhere: column OR data.vm_id.** Store-synthesized events (vm.*, run.*) ride the host-wide stream with a NULL vm_id column; VM linkage lives in `json_extract(payload, '$.data.vm_id')`. `store.Query` applies the two-clause match (column OR data.vm_id) unconditionally whenever VMID is set — no knob, no per-family branch. The API and CountEventsForReport both use the same query path, keeping counts and reproduce_queries congruent (P-05). No family needs special-casing in the API handler.
- **Reconcile report gen must stay synchronous.** `reconcileRuns` calls `m.reportGen(runID)` synchronously (not in a goroutine) so tests that check enqueued IDs immediately after `NewManagerWithReportGen` see the results. The `postConclude` path wraps in a tracked goroutine because it fires from an event-driven path. Don't make reconcile async without updating the existing `TestReconcileTerminalRunMissingReport` test.
- **Every manager goroutine must start via `GoTracked`.** Direct `go` + `wg.Add` races `Close()`'s gate. `GoTracked` holds the read lock while doing `wg.Add`, and `Close()` holds the write lock while setting `closed=true` — this eliminates the race. Any direct `go func()` inside `Manager` bypasses the closing gate; `Close()` can return while the goroutine is still running and touching the store. Pattern: call `m.GoTracked(func() { ... })`, check the bool, log if false and return. If `GoTracked` returns false the manager is closing; dropped work is repaired by Reconcile on next start.
- **Auth middleware injects identity on every non-exempt route.** Handlers downstream of `withAuth` may call `auth.IdentityFrom(ctx)` and treat a missing identity as a bug, not a user error. Only GET /meta and POST /auth/login are exempt; everything else — including GET /auth/session — passes through the boundary.
- **Cross-owner access must answer the standard 404 writer, never a distinct 403.** §14 groups "unauthorized / not found" into a single typed 404 `not_found` response (existence hiding). Any handler that checks ownership must call `writeError` with 404 and cause `not_found` on a mismatch — a 403 leaks existence to the wrong owner.
- **Token secrets exist in exactly two places: the mint response and the operator's memory.** `CreateToken` returns the raw secret once; only its SHA-256 is stored. Logs, events, and list responses carry IDs only. Never log, echo, or include the `secret` field in any response other than the mint 201.
- **`require_authentication: false` is loopback-only dev mode.** Config validation rejects it with any non-loopback `server.mode`. The smoke runs with `require_authentication: true`; the example config's `false` is the dev default, not a production option.
- **`scripts/linux` rsyncs via SSH then runs a command remotely.** Usage: `scripts/linux '<shell command>'`. It excludes `.git` and `.superpowers` from the transfer. The `--filter='P images/dist/'` rule protects build artifacts in gitignored dirs from `--delete` — macOS openrsync ignores `:- .gitignore` for deletion protection. Setting `VMOBS_LINUX_HOST` or `VMOBS_LINUX_DIR` overrides the defaults.
- **Sudo on aibox03 requires a password.** Agents never sudo. The only NOPASSWD grant is `/usr/local/sbin/vmobs-root-helper`, installed by `scripts/aibox03/setup.sh` (which Doctor Biz must run by hand with password sudo). Any step that needs root on aibox03 before setup.sh has run is a Doctor Biz handoff.
- **`mkfs.ext4 -d <dir>` builds ext4 filesystems rootless.** No mounts, no root required. Used for both rootfs and config disk assembly in the image pipeline and the fixture. The `-d` flag populates the filesystem from a directory tree at creation time.
- **Fixture gate: `//go:build linux` + `VMOBS_FIXTURE=1` env var.** `tests/integration/boot_test.go` and `tests/integration/fixture/fixture.go` are linux-only; the integration test additionally requires `VMOBS_FIXTURE=1` to run. Unset → skip with a printed reason naming `scripts/aibox03/setup.sh`. Never claim the gate passed without running it.
- **`ip -json route` shows the main table only — VPN routes are invisible.** On aibox03, tailscale routes live in routing table 52 (policy routing). Use `ip -json route show table all` to see all routes. ParseIPRoutes filters out non-transit entries (type=local/broadcast/multicast) by the "type" field. The blessed invocation is the table-all form everywhere §10.1 collision detection is needed.
- **Find a jailed firecracker by its pid file, never by `pgrep`.** Jailer writes the child PID to `$JAIL_BASE/firecracker/<id>/root/firecracker.pid` under `--daemonize`; that is the documented handle, and `jail-stop` uses it. `pgrep -f <id>` over-matches — every path under the jail carries the VM id, so it also hits a runner dialing that jail's `v.sock`. A pattern that pins the flag instead bets on jailer's exact argv spelling: v1.16.1 execs `--id` and the id as two *separate* elements (`.args(["--id", &self.id])` in `src/jailer/src/env.rs`), with argv[0] the in-jail path `/firecracker`. The pid file bets on nothing.
- **Jailer chmods its chroot root to 0700 mid-startup — after the helper's own chown.** With `--daemonize` the tightening can land after `jail-start` returns, so a post-jailer `chmod` must wait for firecracker to bind `v.sock` (which strictly follows jailer's chroot prep) before reopening the dir to `0750`. Without that, the fixture uid can never traverse to the socket and every dial is EACCES.
- **A dial made with a nearly-expired context reports "i/o timeout", not the real error.** `waitForVsock`-style retry loops must not let a final doomed attempt overwrite the last real dial error (`ctx.Err() == nil` guard before recording). The first M0 gate run reported `i/o timeout` for what was a persistent `permission denied` — one misleading string, a full debug detour.
- **`/run` is a fresh tmpfs under systemd — guestd must create its own mountpoint.** Nothing pre-creates `/run/vmobs/config`; `LoadBootConfig` does `os.MkdirAll` before `unix.Mount` or guestd dies at boot with ENOENT. The failure was invisible on the serial console (unit stderr never surfaced even with `systemd.journald.forward_to_console=1`) — it took an `init=/bin/sh` boot driven over `screen` to see it.
- **The rootfs docker script is ONE host-side double-quoted string — a raw `"` inside truncates it silently.** `images/rootfs/build.sh` passes the whole container script via `bash -c "..."`; an inner `echo "..."` ends the argument early, the rest becomes unused positional args, and the container exits 0 having done almost nothing. `${VARS}` expand host-side even inside inner single quotes, so single quotes are correct there. Guards now: stale inventory removed pre-run, and mkfs refuses a tree missing `vmobs-guestd`/`guestd.service`. be420fd's "log quoting" cleanup caused exactly this.
- **Evidence must be captured when the observation happens, not when the file is written.** The M0 evidence writer re-stat'd jail paths after teardown and recorded six ENOENTs where ownership proof belonged. `statHostFiles` now returns its formatted observations and the writer prints them verbatim — assertion and evidence share one source.
- **A caller's revision pin rides the FIRST transition of an action, and only that one.** `ExpectedRevision` is an optimistic-concurrency precondition: check it once, on the first `TransitionVM` the call makes. `stop`/`force_stop` passed it to both the running→stopping transition and the shared stopped tail, so every pinned stop — i.e. every stop over HTTP, where the pin is mandatory — answered 409 `revision_mismatch` for a VM that really stopped. Don't re-pin the tail to a fresh revision either; that re-opens a race against whatever legitimately touches the VM while `rt.Stop` runs. `Manager.Delete`'s force path obeys the same rule: the pin rides whichever of running/paused→stopping→stopped→deleting runs first, and one `pin` local, cleared on the first transition that actually succeeds, is the whole mechanism in both methods. A transition refused as *invalid* consumed nothing, so the pin travels on — the tolerance for `InvalidTransitionError` can't swallow a `RevisionMismatchError`, since each type's `Is` matches only its own type.
- **Check the precondition before the destructive call, not after.** A revision-pinned transition must run before the runtime side effect it guards (`doAction` transitions to `stopping` before `rt.Stop`; `Delete` before `rt.ForceStop`): a precondition checked after the destructive act is not a precondition — it kills the VM and *then* answers 409, leaving the row reading `running` for a VM that is gone. The cost of the order is that a failed `rt.ForceStop`/`rt.Stop` leaves the row at `stopping`, which is the honest record of "we asked it to die and don't know how it ended". Reconcile owns the recovery, but only at the next controller restart — it runs once, inside `NewManager`/`NewManagerWithReportGen`, not on any periodic sweep while the controller keeps running.
- **A precondition failure must be a typed error or the API blames storage.** `writeVMError` maps types, so an untyped `fmt.Errorf("start requires stopped state…")` fell through to the 500 catch-all: `code: internal, cause: storage_failure, retryable: true` — a lie about a caller-side mistake (P-06). Actions the VM's state refuses return `*store.InvalidTransitionError{From, To}`, which already renders as 409 `invalid_transition` with `details.from`/`details.to`.
- **`POST /vms` is the create/start request — it launches.** `CreateVM` → `enqueueLaunch` → `runLaunch` → `rt.Launch` drives the VM to `running` on its own. There is no separate start action to issue after a create; one will be refused with "start requires stopped state, got running". Concurrent creates ARE concurrent launches (capped by `max_parallel_provisions`).
- **The lock's artifact paths resolve against the lock file's own directory.** `runtime.lock.json` records `images/dist/vmlinux` relative to the tree it was written from, so `jailer.Config.RepoRoot` must be `config.Runtime.ArtifactRoot()` (= `filepath.Dir(lock_file)`). Pointing it anywhere else — the state dir, say — makes every launch die in `doStage` with `artifact hash mismatch: [… Got:absent …]` before privd is ever contacted. The default `lock_file` is relative, so it resolves against the daemon's working directory; production configs want an absolute path.
- **debugfs writes into an ext4 with a dirty journal get clobbered on next boot.** Injecting files with `debugfs -w` into an image that then mounts rw replays the journal over the injected blocks — the "file" can end up pointing at unrelated data. Debug conclusions drawn from debugfs-injected images are unreliable; rebuild properly instead.
- **A VM in `stopping` belongs to whoever put it there.** The spool importer's `NotifyVMMExit` must no-op on `stopping` rather than finish the stop: the initiator (a `stop`/`force_stop` action, `Delete`'s force path, a batch stop wave) holds the graceful-vs-forced determination that only `rt.Stop` returns, and its operation record depends on writing that terminal transition itself. When the importer won the race — easy, since `rt.Stop` spends seconds tearing down a jail while the importer ticks every 5s — the initiator's tail answered `409 invalid_transition from:stopped to:stopped` for a stop that had genuinely worked, and the reason on the row became the importer's instead of `graceful_stop`. A `stopping` row whose initiator died is `Reconcile`'s to recover at the next controller start — the same safety net the stop and force-delete paths already lean on when `rt.Stop`/`rt.ForceStop` fails.
- **SIGKILL is asynchronous, and privd refuses `release_vm` while the VMM is alive.** `Adapter.doStop` used to signal `kill` and ask for the release in the same breath; privd answered the typed `invalid_state` "vm process is still alive; signal first" and the adapter discarded it, so the jail chroot survived (1.7 GB on the host in live gate run 4) and `entry.PID` stayed non-zero — which made `release_network` write a partial ledger entry back instead of deleting the file, leaving it immortal. Any caller of `ReleaseVM` right after a signal must retry while the cause is `invalid_state`; every other cause is a real failure and must be taken as the answer. The error is still discarded at that call site on purpose: returning it would reach `Manager.doAction`'s stop/force_stop cases, which route any error into `failAction` and would record a genuinely-dead VM as a failed stop.
- **A leak test that never takes the leaking path is vacuous evidence.** AT-018's five cycles all stopped gracefully before deleting, so the subtest stayed green beside a real 1.7 GB leak — the leak only appears on `DELETE ?force=true`, which is the only route to `ForceStop`. When a resource check covers a lifecycle, it must exercise every teardown route, not just the polite one.
- **Unix socket paths cap at 108 bytes, and `t.TempDir()` spends most of them on the test name.** A jailer test whose name ran ~40 chars pushed `<tmpdir>/.../v.sock` past the limit and every dial failed with `listen v.sock: bind: invalid argument` — nothing about length in the message. Keep linux-only jailer test names at or under ~31 characters (`TestStopForcedOnIgnoredShutdown` is the working ceiling in `internal/jailer`).
- **No S5 in this guest's ACPI tables — check the boot console before tuning grace-period timers.** Firecracker v1.16.1 hands the guest ACPI tables that advertise only `ACPI: PM: (supports S0)`, never S5 (soft-off). `systemctl poweroff` still runs a complete, clean systemd shutdown — every unit stopped in order, in well under a second — and then the kernel halts instead of powering off: the vCPU parks in HLT and Firecracker never exits. That much was observed directly; the mechanism behind it (no S5 data, so no power-off handler is registered and `sys_reboot` downgrades POWER_OFF to HALT) is inferred from kernel source, never instrumented in the guest. No grace period is ever long enough; the guest was never going to signal it. Firecracker cannot reboot a guest either, so the only working exit door is a guest-initiated restart: `reboot=k` (already in the boot args) makes the kernel write the i8042 reset byte directly, which Firecracker catches and exits on. `defaultPoweroff` in `internal/guest/agent.go` runs `systemctl reboot`, not poweroff, for exactly this reason — see the comment there before "fixing" it back.
- **Never derive a new mutation budget from a recovery context — the tail marker is inherited and silently eats the new budget's tail.** `Manager.recoveryContext` stamps a private `recoveryTail{}` value on every context it makes, so a second call on the same tail returns it unchanged rather than stacking another `recoveryBudget`. Context values survive both `WithoutCancel` and `WithTimeout`, so anything building a *new* mutation budget out of a recovery context — `detachedContext`, `OperationContext` — carries that marker in, and the mutation it starts is denied a tail of its own: the writes that record how it ended run on whatever the parent tail had left, with no error anywhere. Nothing does this today; every such derivation starts from a request context. Rule: derive a new mutation budget from a caller's request context or `m.ctx`, never from a tail.
- **Drain HTTP response bodies before closing them in tests that then shut the server down.** Go 1.27's transport handles an early `Body.Close()` by draining the remainder and reusing the connection, but it releases the caller *before* `tryPutIdleConn` returns the connection to the idle pool. A second request issued in that window finds the pool empty, queues a dial, and is then handed the original connection anyway — leaving a freshly dialed, fully handshaked connection parked in the pool having never carried a request. The server counts it as `http.StateNew`, and `Server.Shutdown` will not close a `StateNew` connection until net/http's hardcoded 5s grace expires (`unixSec < now-5`, so really 5–6s), which outlasts `serve`'s own 5s shutdown budget — `shutdown: context deadline exceeded`, 3.3% of runs on aibox03 (Go 1.27.0), never on darwin (Go 1.26.6 has no drain path, so the unread body just kills the connection and no spare is dialed). Reading to EOF orders the pool return ahead of `Close`. The same race outside tests — any client holding an idle-but-unused connection at SIGTERM — made `vmobsd` log `daemon failed` and exit 1 on an otherwise clean shutdown; fixed in 54d571b by sizing the shutdown budget against that grace (next entry).
- **Size a shutdown budget against net/http's `StateNew` grace, not against handler latency — and size a test's wait above the budget.** `Server.Shutdown` will not close a connection it accepted but read no request byte from until `closeIdleConns` releases it: `if st == StateNew && unixSec < time.Now().Unix()-5` (net/http issue 22682). That clock starts when the connection was accepted, not when shutdown began; it compares whole seconds, so the grace runs 5-6s; and `Shutdown` only re-checks on an interval that ramps to `shutdownPollIntervalMax` (500ms), so it can miss a reclaim it did not cause. Worst case the connection clears ~6.5s after it was accepted, which is why `serve`'s budget is 10s (`cmd/vmobsd/main.go`) and must not be tidied back down to match the 5s `ReadHeaderTimeout` above it -- separate knob, separate clock. The same rule one level up: every test that waits for `serve` to return after `cancel()` uses `shutdownWait` (`cmd/vmobsd/main_test.go`), which must stay above the budget, or a hung shutdown and a merely slow one report identically. `TestShutdownOutlastsParkedConnection` pins the whole thing by parking one pre-handshake and one post-handshake connection -- both are `StateNew` server-side, on two different deadlines, which is what makes it deterministic rather than a 99.8% coin flip.
- **The /30 prefix allocator never gives a prefix back — size a pool for the daemon's whole lifetime, and read exhaustion as "restart the daemon", not "find the leak".** `internal/network/alloc.go` has `Next()` and `Exclusions()` and nothing else: `Next()` walks a cursor forward, no release, free or return path exists, and `internal/jailer/launch.go` calls `Next()` once per fresh launch (a restart reuses the CIDR in the manifest). Built once per daemon over two /16 pools (`cmd/vmobsd/runtime_linux.go`), that is 32,768 /30s per daemon lifetime; a rolled-back launch and a deleted VM never return theirs, and only a restart resets the cursor. The AT-005 recovery launches pass because each subtest's pool is sized for two launches, not because anything was freed. Reclamation is an M1b candidate (PLAN.md deviations log).
- **A cleanup guarded on a recorded stage skips exactly the failures that happen before the record.** `doRollback` removed the stage dir only when the manifest named `staged`, and `staged` is written after `doStage` returns — so every `doStage` failure kept the stage dir forever, and the rollback then deleted the manifest `Release` would have needed to find it. `os.RemoveAll` on a missing path is a no-op; remove unconditionally (`doRelease` already did). Before guarding any cleanup on a record, ask what happens to a failure between the side effect and the record.
- **A chmod-based injection lands on the first syscall that touches the directory, not on the step the test is named for.** `manifest_write_failure` chmodded `vms/` 0555 and failed at `MkdirAll`, never reaching `writeManifest`; three reviews inherited the name. To fail one specific write, re-exec the test binary as a child with `RLIMIT_FSIZE=0` (`launchWriteFailHelper` in `internal/jailer/inject_linux_test.go`): the first `Write` gets EFBIG, nothing else is touched, and the parent's `testing` package keeps its own log writes. Lowering the rlimit in-process trips those log writes; a 0555 dir also blocks the unlink a fix may need, which makes a restart test vacuous.
- **A missing record is not proof the resource is gone — probe the host.** Three separate leaks on this branch shared one shape: `doRollback` deleted the manifest whether or not its `release_vm` landed, `Reconcile` finalized a `deleting` row without ever retrying `Release`, and `doStop` read a missing manifest as "already gone" and answered success — so `Release` early-returned nil on the same missing manifest and `Delete` wrote `deleted` over a microVM that was still running, every call reporting success. Anything that treats the manifest, a recorded stage, or a `deleting` row as evidence of what exists on the host is wrong the moment the record is destroyed before the resource. `doStop` now stats `<JailBase>/firecracker/<id>` when the manifest is missing; absent stays the silent no-op, present means tear it down and let the filesystem, not privd's return value, decide the verdict; `Release` does the same on the same missing manifest, running `release_vm` **before** `release_network` because whichever release empties the last half of a ledger entry makes privd delete it, after which the other answers `not_found` and the chroot is unreachable forever. That gap is closed now: `doRelease` (`internal/jailer/stop.go`) is one path regardless of whether a manifest exists, and it runs `release_vm` unconditionally too, with no stage guard on either verb. The case that forced it: a guest that shuts itself down reaches `stopped` via `NotifyVMMExit`, so `Delete` never force-stops it and goes straight to Release with the manifest still there — a present manifest is a record of what `launch.go` believed it had done, not evidence of what privd or the filesystem still hold, same as the missing-manifest case above.
- **privd's `start_vm` rollback has no start time to check, so it checks `comm` *and* the VM id in the argv.** `AbortStartVM` (`internal/privd/vmops.go`) reads `<jailDir>/root/firecracker.pid` to kill a VMM that `cmd.Run()` started before a later read failed. There is no recorded start time for that process — the failure *is* that `StartVM` never got one — and `StartVM`'s `MkdirAll` does not clear the tree, so the pid file can name a recycled pid. The guard is two `/proc` reads: `stat`'s comm field must read `firecracker`, **and** `/proc/<pid>/cmdline` must carry `--id` and this VM's id as two adjacent argv elements. comm alone is not enough on a host whose whole job is running firecrackers — the process that inherits a recycled pid is disproportionately *another VM's* VMM, which comm cannot tell apart, and SIGKILLing a healthy neighbour is worse than the leak this rollback prevents. **Never identify a jailed VMM by `/proc/<pid>/root`.** The jailer unshares a mount namespace, `pivot_root`s into the jail and detaches the old root, so the jail root is a mount only inside the VMM's own namespace and the host cannot express it as a path: a readlink comparison there matches nothing and withholds *every* kill. `cmdline` reads the same from any namespace, and is world-readable, which matters because the VMM runs as another uid. Match argv elements, never a substring of the joined line — every jail path carries the VM id, the runner's `--uds` among them. Jailer v1.16.1 execs firecracker with `--id` and the id as separate elements (`.args(["--id", &self.id])` in `src/jailer/src/env.rs`), not `--id=<id>`; if that ever changes, every withheld kill logs the argv it saw. Anything that leaves identity unproven withholds the kill and logs it. Do not "simplify" either check away, and never into a bare `Kill(pid)`. An empty `cmdline` has two causes, not one: a zombie has no mm, **and** a live process momentarily has no argv — `execve` sets `comm` before it sets the new mm's `arg_start`/`arg_end`, and Go's `cmd.Start()` returns inside that window, so a just-spawned process can read comm `firecracker` with an empty argv while its state is `R` (measured: 7 empties in 500 spawns). Production never sees it — `firecracker.pid` is written after exec — but any test that spawns a stand-in and reads its argv must wait for the argv to appear (`waitForArgv`, `internal/privd/vmops_jailguard_linux_test.go`) or it fails about one run in five.
- **`RunnerPID` has a partner field: `RunnerStart`.** `runnerAlive` used to stat `/proc/<pid>` and call whatever was there the runner, so a recycled pid read alive — `doStop` would try a graceful shutdown through a ctl socket nobody serves, and `Reconcile` would report a VM adopted whose runner is gone. Both spawn sites (`launch.go`, `respawnRunner` in `stop.go`) now record `/proc/<pid>/stat` field 22 and the check goes through `privd.PIDAlive`. Assign it unconditionally at every spawn: a previous boot's start time next to a new pid makes a live runner read dead. An empty value keeps the old pid-only answer on purpose (old manifests, and spawns whose read lost the race with an instant death) — reporting those dead would let `Reconcile` spawn a second runner onto a live VM.
- **The linux-only suites do run from a Mac — in a container, as a non-root user.** `internal/jailer`'s and `internal/privd`'s `//go:build linux` files never compile on darwin, so `scripts/check` proves nothing about them; a `golang:1.26` container with the repo mounted at `/src` runs them for real. Four traps. Run as a non-root uid (`--user 1000:1000`) or the chmod-based injection subtests fail outright — root's `MkdirAll` ignores a 0555 directory, and `TestInject/state_dir_mkdir_failure` says so rather than skipping — and give the build cache a volume that uid can write. A bind-mounted macOS directory is not that volume: `GOCACHE` on one fails `permission denied` under `--user 1000:1000`; use docker-managed volumes `chown`ed to the uid. Stock `golang:1.26` also has no `mkfs.ext4` — ten `internal/jailer` tests build real ext4 images and fail without it, which is easy to misread as a code failure; run them on a `FROM golang:1.26` + `apt-get install -y e2fsprogs` derivative. What the container still cannot prove: it is whatever arch your Mac is (arm64, not the amd64 the host runs), there is no KVM, and `tests/integration` needs a real Firecracker. A green container run is evidence about logic, never about the host.
